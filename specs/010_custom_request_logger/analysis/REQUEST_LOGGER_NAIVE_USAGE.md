# Request Logger — Step-by-Step Setup and Usage

The course repository already includes the **request logger**. You do not install a separate global package for it.

Its purpose is to make the otherwise hidden agent request visible: it runs as a small local proxy between your coding agent and the model provider, forwards requests unchanged, and writes readable copies to disk.

## 1. Open the course project in PyCharm

Open:

```text
ai-coding-crash-course/
```

Then open the integrated terminal:

```text
View
→ Tool Windows
→ Terminal
```

Make sure the terminal is in the repository root.

Verify with:

```bash
pwd
```

You should be inside something like:

```text
.../ai-coding-crash-course
```

You can also check:

```bash
ls
```

---

## 2. Make sure project dependencies are installed

If you already ran this during the project setup, you do **not** need to run it again.

Otherwise:

```bash
npm install
```

The request logger is part of the course repository, so the repository's dependencies need to be available.

---

## 3. Create a dedicated PyCharm terminal tab for the logger

I recommend three terminal tabs:

```text
PyCharm
│
├── Terminal 1
│     npm run dev
│
├── Terminal 2
│     npm run request-logger
│
└── Terminal 3
      agent launched through logger
```

This is easier than stopping and restarting processes in a single terminal.

---

# 4. Start the Request Logger

In **Terminal 2**, from the repository root, run:

```bash
npm run request-logger
```

This is the command specified by the course.

On the first run, the logger asks a few interactive questions.

---

# 5. Select Your Coding Agent

The logger asks which coding agent you are using.

For example, select:

```text
Claude Code
```

If the selected agent supports multiple model providers, it may additionally ask which provider you use.

Then it may ask whether it should remember the selection for future runs.

You can let it remember your choice.

---

# 6. Confirm the Logger Is Running

After setup, the logger starts a local web server at:

```text
localhost:8787
```

More importantly, it prints an **exact command for launching your selected coding agent through the logger**.

Your terminal will conceptually look like:

```text
Request logger running...

localhost:8787

Launch your agent using:

<generated command here>
```

## Important rule

Do **not** try to reconstruct this command manually.

Copy exactly what the request logger prints.

The course explicitly warns about this because the required command depends on the agent/provider, and some agents may also require a small configuration file.

---

# 7. Keep the Logger Running

Do not close Terminal 2.

Think of the architecture as:

```text
Claude Code
     │
     ▼
Request Logger
localhost:8787
     │
     ▼
Model Provider
```

The logger sits in the middle.

If you stop the logger, the specially launched agent session can no longer send requests through it.

---

# 8. Open a Second Terminal for Claude

In PyCharm, open another terminal tab.

Call this **Terminal 3**.

Again make sure you are inside:

```text
ai-coding-crash-course/
```

---

# 9. Copy the Generated Agent Command

Go back to Terminal 2.

Find the command printed by:

```bash
npm run request-logger
```

Copy it.

Now paste that command into Terminal 3 and execute it.

**Do not simply run:**

```bash
claude
```

for this experiment.

A normal `claude` invocation may talk directly to the provider and bypass the logger.

For the logger experiment you want:

```text
generated command
       ↓
Claude Code configured to use logger
       ↓
localhost:8787
       ↓
model provider
```

The course states that the configuration is established when the agent starts, so the agent must be launched using the command generated by the logger.

---

# 10. Send a Test Message

Once Claude Code starts through the logger, type something deliberately tiny:

```text
Hello!
```

or:

```text
Say hello.
```

Claude should respond normally.

The logger is intended to be transparent, so using Claude should feel essentially unchanged.

At this point the flow is:

```text
You
 ↓
"Hello!"
 ↓
Claude Code harness
 ↓
Request Logger
 ↓
Anthropic/model provider
 ↓
response
```

---

# 11. Find the Generated Logs

Now go back to the PyCharm project explorer.

Open:

```text
request-logger/
└── logs/
```

After sending a request, timestamped files should appear there.

The timestamps are stored in **UTC**.

If PyCharm does not immediately display new files, refresh the Project pane.

---

# 12. Open the `.md` Log First

For each captured request, the logger creates three representations:

```text
*.md
*.request.txt
*.response.txt
```

The important one for normal inspection is:

```text
.md
```

Open the **newest `.md` file** first.

The course explicitly calls this the readable representation and recommends starting there.

The files mean:

| File | Purpose |
|---|---|
| `.md` | Human-readable representation |
| `.request.txt` | Raw/verbatim request body |
| `.response.txt` | Raw response stream |

---

# 13. Inspect What Was Actually Sent

Inside the `.md` file, look for structures such as:

```xml
<meta>

<headers>

<request>

    <params>
    </params>

    <system-prompt>
    </system-prompt>

    <tools>
    </tools>

    <messages>
    </messages>

</request>

<response>
</response>
```

This is the key learning exercise.

Your visible request may have been only:

```text
Hello!
```

but the actual request sent by the harness contains much more.

---

# 14. Inspect `<system-prompt>`

Find:

```xml
<system-prompt>
```

Read through it.

This is the standing instruction set supplied by the coding harness.

It can contain information such as:

```text
working directory
platform
agent instructions
session guidance
behavioral rules
```

The crucial mental model is:

```text
What you type
≠
everything the model receives
```

Instead:

```text
system prompt
      +
tool definitions
      +
other harness context
      +
conversation
      +
your prompt
      ↓
    MODEL
```

---

# 15. Inspect `<tools>`

Now find:

```xml
<tools>
```

Scroll through it.

This section can be surprisingly large because the agent needs to tell the model:

- which tools exist;
- what each tool does;
- which parameters it accepts;
- how outputs are structured.

This helps explain why an apparently trivial interaction can involve a large request.

---

# 16. Inspect `<messages>`

Find:

```xml
<messages>
```

Locate your:

```text
Hello!
```

You may also find messages injected by the harness itself.

This illustrates another important distinction:

```text
conversation you see
          ≠
full message sequence sent to model
```

---

# 17. Inspect `<response>`

At the end, find:

```xml
<response>
```

This contains information associated with the model response, including token-use information described in the course.

The exercise is designed to reveal the hidden cost and structure of an apparently tiny interaction.

---

# 18. Don't Panic If You See Two Requests

You may notice that:

```text
1 user message
```

creates:

```text
2 log entries
```

with Claude Code.

That does not necessarily indicate duplicate execution.

The course explains that Claude Code may send a small **quota probe** when it starts. It is a deliberate tiny request used to check subscription headroom and may even appear as a `429` entry. The actual user turn is logged separately.

So:

```text
log #1 → startup/quota probe
log #2 → your real prompt
```

can be perfectly normal.

# 20. How to Stop the Logger

When you're finished with the experiment, go to the terminal running:

```bash
npm run request-logger
```

and press:

```text
Ctrl+C
```

You can also terminate the special Claude session.

Afterwards, for ordinary course work, launch Claude normally again:

```bash
claude
```

The request logger is primarily an introspection/debugging tool; it does not need to stay running for all your course work.

# 21. Quick Troubleshooting

## `npm run request-logger` fails

First verify you're in the course repository:

```bash
pwd
```

Then verify dependencies are installed:

```bash
npm install
```

Then retry:

```bash
npm run request-logger
```

---

## Logger runs but no logs appear

Check these in order:

```text
1. Is npm run request-logger still running?
2. Did you launch the agent using the EXACT command printed by it?
3. Did you send a message after launching that agent?
4. Are you looking inside request-logger/logs/?
```

The most likely conceptual mistake is:

```bash
npm run request-logger
```

followed by opening another terminal and simply running:

```bash
claude
```

That may bypass the proxy.

Instead use:

```text
whatever command the logger printed
```

---

## `localhost:8787` doesn't look like a normal application

That's okay.

The point of this lesson is **not primarily to browse a website at port 8787**.

The important outputs are:

```text
1. generated agent-launch command
2. captured files in request-logger/logs/
```

The logger is acting as a proxy.

# 23. Flashcards to Add to the Glossary

### Request Logger

A local proxy included in the course repository that sits between the coding agent and model provider and records readable copies of requests.

**Command:**

```bash
npm run request-logger
```

---

### Proxy

An intermediary through which communication passes.

For this exercise:

```text
Agent → Proxy → Model Provider
```

The request logger acts as the proxy.

---

### `localhost:8787`

The local address used by the course request logger while it is running.

---

### `.md` Request Log

The human-readable representation of a captured model interaction.

**Use this one first.**

---

### `.request.txt`

The verbatim request body recorded by the logger.

Useful when you need the raw representation rather than the readable render.

---

### `.response.txt`

The raw response stream recorded by the logger.

---

### System Prompt

Standing instructions inserted by the harness rather than manually typed by the user.

Visible inside:

```xml
<system-prompt>
```

in the readable request log.

---

### Tool Schema

Structured instructions describing tools available to the model.

The schemas themselves consume model context and may be surprisingly large.

---

### Quota Probe

A small startup request that Claude Code may issue to check subscription headroom.

It can produce an extra request-log entry, so **two logs for one visible user message can be normal**.

---

# 24. Memory Shortcut

Remember the logger workflow as:

```text
START
  ↓
npm run request-logger
  ↓
SELECT AGENT
  ↓
COPY GENERATED COMMAND
  ↓
NEW TERMINAL
  ↓
RUN GENERATED COMMAND
  ↓
SEND PROMPT
  ↓
request-logger/logs/
  ↓
OPEN NEWEST .md
  ↓
system-prompt
tools
messages
response
```

The key rule is:

> **Start logger → launch agent through the command it gives you → inspect the newest `.md` file.**
